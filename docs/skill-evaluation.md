# ROS 2 스킬 평가 기록 규격

## 목적과 저장 위치

설치된 ROS 2 스킬이 실제 개발 판단·검증에 미치는 영향을 추적합니다. 이 문서는 기록 규격이며 프로젝트의 실행 일지가 아닙니다.

원본 이벤트는 설치 스킬의 `references/usage-recording.md`에 지정된 **저장소 밖 평가 루트**의 `usage.jsonl`에 추가합니다. 프로젝트별 집계·근거 목록은 이 저장소 옆 `Oh_My_SLAM_skill_evaluation`에서 관리합니다. 실제 로그·개인 평가 자료는 이 공개 저장소에 커밋하지 않습니다.

## 적용 조건

| 스킬 | 적용 대상 |
| --- | --- |
| `ros2-development` | ROS 연결 설계, 패키지·노드·interface·launch·설정 구현, 빌드·검증 |
| `ros2-troubleshooting` | 실행 상태가 필요한 QoS, TF, IMU, odometry 문제의 진단 |

한 스킬을 읽고 현재 작업에 적용하지 않은 경우는 `review_only`로 기록하며 실제 적용 횟수에 더하지 않습니다. 참고 파일을 여러 번 열거나 하나의 적용을 여러 턴에 걸쳐 수행해도 사용 횟수가 늘어나지 않습니다.

## 이벤트 모델

| 필드 | 의미 |
| --- | --- |
| `usage_id` | 논리적인 한 스킬 적용의 식별자. 같은 적용의 start/observation/finish가 공유 |
| `event` | `start`, `observation`, `finish` |
| `recorded_at` | 실제 기록 시각·시간대 |
| `skill`, `installed_file_sha256` | 적용한 스킬과 설치본 버전 근거 |
| `workspace`, `application` | 대상 프로젝트와 적용 방식 |
| `instruction` | 실제 판단에 사용한 지침 |
| `action` | 해당 지침에 따라 수행하거나 달리 결정한 내용 |
| `result`, `artifacts` | 실제 결과와 검증 가능한 근거 경로 |
| `helpfulness` | `helpful`, `partial`, `not_helpful`, `unclear` 및 판정 이유 |
| `benefit_assessment` | 관측 결과, 기존 지식/사용자 규칙과의 중복, 인과 효과의 확인 수준 |
| `costs` | 실제 관찰한 추가 도구 호출·실패·재작업. 측정하지 않은 시간·토큰·비용은 null |

계획은 `declared_plan`, 실제 관찰은 `observed`, 도움 해석은 `assessment`로 구분합니다. 실행하지 않은 테스트·실물 효과를 finish 결과에 넣지 않습니다.

## 집계 정의

- **실제 사용 횟수:** 프로젝트에 속하는 고유 `(usage_id, skill)` 중 실제 적용 이벤트가 있는 수.
- **완료 수:** 위 적용에 `finish` 이벤트가 있는 수. 진행 중 수는 실제 사용 횟수에서 완료 수를 뺍니다.
- **열람 건수:** 실제 적용이 없는 `review_only` 논리 건수. 파일 읽기 횟수가 아닙니다.
- **도움 판정:** 완료된 적용의 최종 판정을 집계합니다. 판정 미기록은 `unclear`로 남깁니다.
- **도움 비율:** 충분한 사례가 쌓인 뒤 helpful/partial/not_helpful/unclear를 따로 공개합니다. partial을 성공으로 합쳐 하나의 성능 개선율처럼 표현하지 않습니다.

중복 이벤트는 사용 횟수를 늘리지 않습니다. 정정 이벤트가 있으면 원본을 보존하고 최근 판정을 사용합니다.

## 도움 판정과 성능 주장의 경계

| 판정 | 요구 근거 |
| --- | --- |
| `helpful` | 특정 지침이 판단·검증 방법을 바꿨고 그 결과가 근거로 확인됨 |
| `partial` | 일부 구조화·누락 방지에 도움이 됐지만 기존 규칙과 겹치거나 독립 효과는 분리되지 않음 |
| `not_helpful` | 실질적인 판단 변화가 없었거나 적용으로 생긴 불필요한 비용이 확인됨 |
| `unclear` | 판단이나 실행 근거가 부족해 도움을 판정할 수 없음 |

테스트 통과는 작업 결과이지 스킬 성능 향상의 증거가 아닙니다. 코드 직접 조사, 공식 문서, 하위 에이전트의 별도 검토가 발견한 내용을 스킬 덕분으로 바꾸어 기록하지 않습니다. 인과적 성능 개선을 주장하려면 비교 가능한 작업·모델·도구·검증 조건을 갖춘 별도 기준선이 필요합니다.

스킬 기록을 위해 새 로봇 시험이나 장시간 비교 실험을 추가하지 않습니다. 프로젝트 작업에서 자연스럽게 얻은 근거를 우선 사용합니다.
